هذه الوثيقة تثبت أين نعمل، وبأي ترتيب، وكيف نراجع جودة التنفيذ. تحديث 3 نوفمبر 2026 بناءً على توجيه المستخدم: كود مفهوم وقابل للصيانة، تقليل تكرار السلوك، وتجربة بصرية متقنة مع السماح بتحسين التصميم المرجعي ضمن فكرة التطبيق.

## 2. العلاقة بين الأجزاء

```text
Flutter للطالب ───────┐
                     ├── HTTPS / API ── ASP.NET Core ── PostgreSQL
Angular للجامعة ─────┘
```

الواجهة تعرض البيانات وتدير التفاعل. الخادم يطبق الصلاحيات والموافقات ويحسب النتيجة ويحفظها. قاعدة البيانات لا تُفتح للواجهات. PostgreSQL ليس تطبيقًا رابعًا؛ migrations الخاصة به تتبع Backend.

نحافظ على تقنيات المرجع الأساسية: Flutter وAngular وASP.NET Core وPostgreSQL، مع إصدارات مدعومة ومثبتة ومتوافقة عند إنشاء المشاريع. اختيار الخادم المثبت في الخطة .NET 10 LTS. لا ننقل إصدارات التبعيات القديمة تلقائيًا من ZIP.

## 3. من أين نبدأ بالضبط

البداية بالـFrontend والـBackend معًا، بمهام صغيرة مترابطة. أول شريحة وظيفية هي الدخول والموافقات والرئيسية؛ تليها رحلة الفحص والنتيجة. لوحة الجامعة تأتي بعد استقرار أول عقود البيانات والصلاحيات.

### الدفعة الأولى التأسيس

1. **تجهيز بيئة البناء:** التأكد من SDKs، تثبيت النسخ المختارة، وتوليد Flutter وsolution الخادم. توثيق المتطلبات الفعلية. نهيئ Angular في دفعة لوحة الإدارة؛ نثبت مساره الآن.
2. **حسم قرارات الأساس:** ADR قصير لمزود الهوية، وإدارة الحالة والتنقل، والتخزين، ونطاق الجامعة. فحص توفر SSO أولًا؛ إذا لم يتوفر نختار حل هوية موثوقًا بديلًا.
3. **تأسيس الواجهة:** ألوان وخطوط ومسافات وأزرار وحقول وبطاقات وحالات عامة؛ ثم AppShell والتنقل والعربية والإنجليزية والوصول الدائم للمساعدة.
4. **تأسيس الخادم والبيانات:** المشاريع وحدود الاعتماد، إعدادات بيئات، health/readiness، عقد أخطاء، مصادقة، ونموذج الجامعة والحساب والموافقات مع migrations أولية.
5. **ربط أول رحلة:** دخول فعلي في بيئة التطوير ← عرض السياسة الحالية ← حفظ موافقة الخدمة وموافقة بحث مستقلة ← الرئيسية ← إعادة فتح التطبيق مع استرجاع الحالة من الخادم.
6. **مراجعة الجودة والعرض:** نشاهد الرحلة على جهاز أو محاكي ونراجع الشكل والحالات والصلاحيات والاختبارات. نصحح الأساس قبل توسيع الشاشات.

يمكن استخدام هوية تجريبية معزولة أثناء بناء التصميم؛ لا تعتبر رحلة الدخول مكتملة قبل الربط الحقيقي. غياب قرار الهوية لا يمنع بناء المكونات والواجهات وعقد الموافقة، لكنه يمنع إعلان اكتمال المصادقة.

### متى نعتبر الدفعة الأولى منتهية

- تطبيق Flutter والخادم يبنيان بأوامر موثقة ويمكن تشغيلهما محليًا، وCI يشغّل الفحوص ذات الصلة.
- تسجيل دخول وخروج وحفظ الموافقة واسترجاعها يعمل مع API وقاعدة اختبار؛ لا يكتفي بتغيير الشاشة أو متغير في الذاكرة.
- رفض موافقة البحث لا يمنع استخدام الخدمة. يسجل نوع الموافقة ونسخة السياسة ووقت القرار.
- لا يقرأ مستخدم بيانات مستخدم آخر أو جامعة أخرى، مع اختبارات وصول حقيقية.
- شاشة الدخول والموافقة والرئيسية متناسقة وتعمل بالعربية والإنجليزية ومع تكبير الخط، والمساعدة متاحة منها.
- انقطاع الشبكة وفشل الحفظ وإعادة المحاولة لهما سلوك مفهوم، ولا تُعرض عملية فاشلة على أنها محفوظة.
- لا توجد أسرار أو بيانات حساسة في Git أو logs.

## 4. تنظيم الكود داخل التطبيقات

### Flutter

```text
apps/student-mobile/lib/
  app/                      # تشغيل التطبيق والربط والتنقل
  core/                     # شبكة وأخطاء وتخزين وترجمة
  design_system/            # theme وtokens ومكونات مشتركة
  features/
    auth/
    consent/
    home/
    safety/
    screening/              # يضاف عند بدء الميزة
      presentation/
      application/
      data/
      domain/               # عند وجود نموذج أو قواعد فعلية يحتاجها العميل
```

داخل كل ميزة نفصل العرض عن حالته وعن الوصول للبيانات. شاشة بسيطة لا تحتاج طبقات وهمية. استدعاء API يمر من repository مناسب؛ لا يتكرر HTTP ومعالجة أخطائه داخل كل شاشة. لا نكرر خوارزمية احتساب النتيجة السريرية في Flutter.

### Backend

```text
services/backend/
  src/
    Thrive.Api/             # endpoints وتهيئة التطبيق والمصادقة
    Thrive.Application/     # حالات الاستخدام والتحقق من الوصول وواجهات الاعتماد
    Thrive.Domain/          # قواعد المجال والكيانات والثوابت
    Thrive.Infrastructure/  # EF والتخزين ومزود الهوية وخدمات خارجية
      Persistence/
        Configurations/
        Migrations/
    Thrive.Contracts/       # طلبات واستجابات API العامة
  tests/
```

Domain مستقل. Application يستخدم Domain. Infrastructure ينفذ منافذ Application. Api يربط التنفيذ ويعرض HTTP. نرتب ملفات كل طبقة حسب الميزة. تطبيق Backend واحد للنشر؛ فصل المشاريع هدفه وضوح الاعتماد والاختبار.

### Angular

```text
apps/university-admin/src/app/
  core/                     # الهوية وinterceptors وإعداد التطبيق
  shared/                   # مكونات مشتركة فعلًا
  features/
    dashboard/
    services/
    resources/
    referrals/
```

كل ميزة تملك صفحاتها وعرضها وحالتها. العميل المولد يتولى عقود الاتصال؛ الخدمات تضيف سلوك التطبيق عند الحاجة. حواجز التنقل تفيد تجربة الاستخدام، والخادم يتحقق من الصلاحيات في جميع الأحوال.

## 5. كيف نطبق Clean Code وتقليل التكرار

| القاعدة | التطبيق العملي |
|---|---|
| مصدر واحد للسلوك | قواعد احتساب النتائج وتحديد مسار الدعم في الخادم؛ لا نسخ موازية في Flutter وAngular |
| مشاركة UI ذات المعنى نفسه | زر أساسي وحقل إدخال وبطاقة خدمة موحدة داخل كل تقنية، مع variants محدودة وواضحة |
| فصل المسؤوليات | الشاشة تعرض؛ حالة الاستخدام تنسق؛ المستودع يصل للبيانات؛ قاعدة المجال تقرر |
| وضوح الأسماء | أسماء تصف المهمة مثل SubmitScreening وRecordConsent بدل Helper وManager عامين |
| أنواع صريحة | DTOs ونماذج محددة، دون any أو خرائط ديناميكية في منطق التطبيق |
| اعتماديات واضحة | تمرر الاعتمادات بدل إنشاء HTTP أو DB داخل المنطق؛ القواعد تختبر دون شبكة |
| تقليل التعقيد | دوال قصيرة لها هدف واضح، شروط مقروءة، composition، وتجنب الوراثة العامة بلا حاجة |
| أخطاء متناسقة | عقد أخطاء واحد ومعالجة مركزية في حدود الاتصال، ورسائل مفهومة للمستخدم |
| اختبار السلوك | اختبارات للقواعد والصلاحيات والرحلات المهمة، مع تحقق بصري للشاشات |

عدم التكرار يعني مشاركة المعرفة الواحدة. إذا تشابهت شاشتان بالشكل لكن قواعدهما مختلفة، لا ندمجهما في مكوّن ضخم مليء بالشروط. نستخرج الجزء المشترك المستقر ونبقي اختلاف السلوك واضحًا. لا يلزم انتظار تكرار ثابت العدد إذا كان لدينا فعلًا مصدر حقيقة مشترك.

Flutter وAngular تقنيتان مختلفتان؛ لا نحاول مشاركة كود UI بين Dart وTypeScript. نشترك في مواصفة API والمصطلحات ومواصفات التصميم، ونولد نماذج النقل بدل إعادة كتابتها يدويًا عند كل تعديل. أنماط العرض الخاصة بكل واجهة تبقى فيها.

قبل إنهاء أي ميزة نراجع: هل كررنا قاعدة موجودة؟ هل هذا التجريد مفهوم؟ هل نقدر نغير الميزة دون تعديل أجزاء غير مرتبطة؟ وهل الاختبار يمسك الخطأ المتوقع؟

## 6. اتجاه التصميم المعتمد

المرجع يحدد الفكرة والهوية والوظائف الأساسية. يسمح بتحسين توزيع العناصر والمسافات والخطوط والأيقونات وطريقة عرض المعلومات والحركة والتنقل. نحتفظ بروح الألوان والشعار والأسلوب الداعم الهادئ، ونوازنها مع بساطة الاستخدام.

الفخامة هنا تظهر في تفاصيل متناسقة: خط عربي مقروء، مساحات مريحة، أزرار واضحة، محتوى مرتب، حالات فارغة ورسائل خطأ مصممة، وانتقالات خفيفة. نقلل الزحمة البصرية والنصوص الصغيرة في الموكاب، ونستخدم الرسوم عند فائدتها. لا نجعل الزينة تؤخر المساعدة أو تربك قراءة النتائج.

أول مراجعة بصرية تشمل ثلاث شاشات مترابطة: الدخول، الموافقة، والرئيسية، مع مكون المساعدة. بعد مراجعتها نستخرج المكونات المستقرة ونكمل بقية الواجهات. نراجع هاتفًا صغيرًا وآخر كبيرًا، واللغتين، وتكبير النص.

تحسين الشكل لا يغير معنى الموافقات أو تفسير النتائج أو صلاحيات الوصول. هذه تغييرات منتج مستقلة تحتاج سببًا وتوثيقًا ومراجعة ملائمة.

## 7. التشغيل المحلي المستهدف

هذه عناوين التطوير المعتمدة؛ توفر الخدمات يعتمد على تشغيلها محليًا:

| الخدمة | عنوان التطوير المستهدف |
|---|---|
| API على الجهاز | `http://localhost:5280` |
| PostgreSQL على الجهاز | `localhost:55432` |
| Angular dev server | `http://localhost:4300` |
| API من Android emulator الافتراضي | `http://10.0.2.2:5280` |

الاتصال غير المشفر هنا محلي في بيئة development فقط؛ staging وproduction يستخدمان HTTPS. أي استثناء Android للاتصال المحلي يحصر في إعداد debug. الهاتف الفعلي يحتاج عنوان الجهاز على الشبكة أو وسيلة اتصال تطوير مناسبة. base URL إعداد بيئة واحد وليس نصًا موزعًا في الشاشات. Flutter يتصل بالخادم ولا يتصل بمنفذ PostgreSQL. إعدادات الأسرار والاتصال الحقيقية خارج Git.

أوامر البناء والتشغيل موجودة في READMEs الخاصة بالتطبيقات وفي infrastructure/local/README.md. ملفات SDKs المحلية خارج Git. بعض أدوات Flutter وPostgreSQL على Windows تتطلب مسار عمل لاتيني؛ توثق تفاصيل المعالجة المحلية دون نقل ملفات المشروع من المسار المعتمد.
